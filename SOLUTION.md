# Решение задачи №6 — Tender Status Tracker

## 1. Архитектура

Сервис реализован на FastAPI для минимального кода и быстрого API-старта.
Выбранный стек:
- FastAPI — современный асинхронный фреймворк с автогенерацией OpenAPI.
- SQLAlchemy 2.x с Declarative API — прозрачный ORM и типобезопасная модель.
- Pydantic v2 — валидация входящих/исходящих DTO.
- SQLite по умолчанию, PostgreSQL при `DATABASE_URL`.

Приложение разделено на:
- `database.py` — инициализация движка и сессий.
- `models.py` — ORM модели `Tender` и `TenderStatusHistory`.
- `status.py` — перечисление статусов и правило переходов.
- `schemas.py` — схемы запросов/ответов.
- `routers/tenders.py` — все HTTP-обработчики.
- `tests/test_tenders.py` — набор интеграционных тестов FastAPI TestClient.

## 2. Модель данных

`Tender`:
- `id` — PK
- `title` — обязательное название
- `description` и `customer` — optional поля
- `status` — enum из четырех статусов
- `created_at`, `updated_at` — временные метки в UTC

`TenderStatusHistory`:
- `old_status` — предыдущий статус, может быть `NULL` для исторических миграций в будущем
- `new_status` — новый статус
- `changed_by`, `reason` — аудит изменений
- `changed_at` — время изменения в UTC
- `tender_id` — FK на `Tender` с `ON DELETE CASCADE`

## 3. Логика статусов

В модуле `status.py` задается map допустимых переходов:
- `DRAFT -> ACTIVE`
- `ACTIVE -> WON | LOST`

Любой другой переход считается недопустимым. При попытке изменить статус на
тот же, что и текущий, сервис возвращает ошибку конфликта и не создает запись в истории.

## 4. Алгоритм обработки `/tenders/{id}/status`

1. Загружаем тендер по id.
2. Проверяем, что найден.
3. Сравниваем новый статус с текущим.
4. Проверяем правило перехода через `is_transition_allowed`.
5. При успехе:
   - создаем запись `TenderStatusHistory` с `old_status`, `new_status`, `changed_by`, `reason`.
   - обновляем `tender.status`.
   - коммитим транзакцию и возвращаем обновленный тендер.

## 5. Логика логирования истории

Для каждого валидного перехода создается ровно одна запись в истории.
История запрашивается отдельным endpoint'ом и сортируется по `changed_at DESC`,
чтобы первыми были самые свежие изменения.

## 6. Расширение системы

Чтобы добавить новый статус:
1. Добавить значение в `TenderStatus`.
2. Обновить `STATUS_LABELS`.
3. Дополнить/обновить `ALLOWED_TRANSITIONS`.
4. Добавить миграцию БД в отдельном слое (в текущей версии используется `Base.metadata.create_all` для простоты).
